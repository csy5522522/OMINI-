### A01：长标题引起本地与云端内容覆盖

触发条件：同账号存在两篇标题相同、长度达到 160 字符的笔记。网页允许标题最多 240 字符，因此这些输入属于正常允许范围。

原因：镜像路径按标题前 160 字符计算。遇到同名笔记时，代码在标题末尾追加笔记 ID，但重新计算路径时又截断至 160 字符，追加的区分信息消失。两个 ID 最后映射到同一个 `.ominote` 文件。

复现结果：初次同步后数据库有 2 篇笔记、磁盘只有 1 个镜像文件；两篇原本不同的正文，在第二轮同步后变成相同正文。原历史快照仍保留，但当前正文已经发生错误覆盖。

修复建议：镜像文件名直接从稳定的笔记 ID 派生；标题只作为加密内容保存。发现已有路径被另一 ID 使用时中止覆盖并修复映射。增加相同长标题、相同前缀、非法字符归一化碰撞及重复同步测试。

### A02：云端功能开关绕过未保存保护

触发条件：桌面有尚未保存的编辑，此时另一端关闭备忘录功能；本机保存失败，或中文输入法仍在组合输入。

原因：本机设置保存会调用 `prepare_features()` 检查，但云端偏好应用直接进入 `apply_features()`。页面的 `stop()` 调用 `flush()` 后忽略返回值，随后停止自动保存并移除页面。

复现结果：模拟磁盘写入失败后，活动备忘录页面被移除，未保存状态仍为真，自动保存计时器已停止；磁盘只保留旧正文。页面销毁后编辑内容随之丢失。

修复建议：所有功能关闭入口共用保存保护；先保存成功或持久保存加密草稿，再销毁页面。保存失败时保留页面并延迟应用开关。补充来自云端的功能关闭、输入法组合输入和磁盘异常测试。

### A03：切换账号后处理过期课表响应

触发条件：账号 A 正在导入课表、在线刷新或保存学期日期，请求尚未结束时退出并登录账号 B，之后 A 的请求才完成。

原因：上述异步事件处理器在 `await api(...)` 后直接调用 `acceptTimetable()`，缺少其他读取流程已有的 `authGeneration` 校验。

复现结果：当前身份为 `account-b`，课表状态和展示内容却出现 `ACCOUNT A PRIVATE COURSE`。本次确认了界面与内存状态串入；未将跨账号服务端写入作为已确认结论。

修复建议：每个异步处理器捕获账号代次，在应用数据、关闭弹窗和显示结果前校验；退出和切换账号时取消仍在进行的请求。覆盖三个课表写操作的延迟响应测试。

### A04：保存失败后文件已经变化

触发条件：编辑或导入超过 2 MiB 正文。TXT 读取层允许最多 16 MiB，数据库层限制正文 2 MiB。

原因：`save()` 先替换加密镜像，再通过 `record()` 进入数据库长度校验。`create()` 同样先创建文件。后一步失败时，文件与数据库内容已经不一致。

复现结果：保存 2,097,153 字节正文时收到限额错误，但镜像已经变成超限正文，数据库仍是 `ORIGINAL`；把编辑改小后再次使用原摘要保存，收到文件已被其他程序修改的错误。

修复建议：写入前完成统一的正文和标题校验；对镜像、数据库和映射设计可恢复的提交过程，失败时恢复旧状态。明确区分 TXT 导入文件大小与正文内容大小限制。

### A05：连续编辑被误判为并发冲突

触发条件：先将主题从浅色改为深色，在保存请求返回前又改回浅色；课表周次和助手设置也走相同队列。

原因：第二次排队继承旧请求的 `revision`。第一次响应后只更新 `cloudResources`；仍待发送的新编辑没有基于服务器新版本重新建立基准。服务器因此把同一设备连续编辑当成了跨设备冲突。

复现结果：最新选择是浅色，最终保留深色，且待同步队列已经清空。

修复建议：为每种资源串行提交，在响应到达时用新基准重新应用仍待发送的用户改动，保留最新意图。为快速切换主题、连续切周和连续调整权重增加延迟响应测试。本次复现使用符合当前三方合并语义的确定性服务替身。

### A06：丢失响应造成重复冲突副本

触发条件：笔记保存已在服务端提交，客户端在接收结果前断线。

原因：本机确认版本尚未更新，重试发现远端版本领先，就直接生成新随机 ID 的冲突副本；请求和动作缺少端到端幂等标识。

复现结果：只有一篇未发生内容竞争的笔记，一次丢失响应再重试后，云端变成 2 篇，并报告 1 个冲突。

修复建议：为每个离线动作持久生成操作 ID，服务端按账号与操作 ID 去重并返回原结果；在真正存在不同编辑时才创建冲突副本。

### A07：异常队列记录使所有页面一起启动失败

触发条件：`tasks.json` 语法正确，但某条记录缺字段或结构异常，例如 `[{"id":"damaged-row"}]`。

原因：初始化通过列表推导式直接反序列化全部条目，缺少逐条校验与异常隔离；主窗口无论是否开启下载功能都会创建任务管理器。

复现结果：抛出 `DownloadTask.__init__()` 缺少 `type`、`source`、`output_dir` 的 `TypeError`，主窗口初始化中断。

修复建议：逐条验证记录，保留有效条目，将异常条目另存恢复文件，并提示受影响数量。设置文件也应统一验证结构与字段类型。

### A08：下载速度解析失效

触发日志：`[download]  42.0% of 100MiB at 1.23MiB/s ETA 00:47`。

复现结果：真实 `_parse_progress()` 发出进度 `42.0`、速度 `—`、剩余时间 `00:47`。

原因：正则中速度部分为可选组，前后又有宽泛匹配，匹配成功时跳过了 `at` 速度字段。

修复建议：将百分比、速度与 ETA 分别提取，或使用下载引擎的结构化进度输出。补充有速度、无 ETA、未知总大小及不同下载引擎的进度样例。

## 功能改进建议

1. **同步期间保持可编辑。** 当前桌面每 20 秒同步时禁用整个备忘录页面，直到文字、图片和历史处理完毕（`text_notes_page.py:582`）。改用本地快照与后台上传，并显示待同步动作数、失败原因和下一次重试时间；为长任务提供取消。
2. **减少全量读取。** 列表接口返回所有笔记的完整正文，历史接口返回所有完整快照；桌面同步也重复读取历史。建议列表仅返回标题、摘要和版本，正文按需获取，历史分页，按版本增量传输。先用大量笔记和长历史测量耗时、内存及流量。
3. **增加完整备份与迁移入口。** 当前 TXT 导出侧重正文，本机密钥受 Windows 用户绑定。建议提供包含图片、回收站和历史的完整备份包，配套恢复校验及跨电脑迁移流程，并显示最近成功备份时间。
4. **完善账号自助功能。** 增加邮箱验证、找回密码和登录设备管理，降低邮箱误填、账号丢失和重复注册成本。现有 README 已明确尚无邮箱验证码。
5. **设置按用途分组。** 将账号与同步、界面偏好、本机工具、更新分组，标明哪些随账号同步、哪些只作用于当前电脑；在同步冲突入口提供字段差异与恢复预览。
6. **统一测试与依赖入口。** 增加一条可重复执行的检查命令，声明 JavaScript 测试所需依赖；目前两套前端测试依赖 `.cache/web-test` 和编辑器目录里的包。CI 分别覆盖 Windows Qt、Linux Web + MySQL 和 Chromium，加入本报告的边界场景。
7. **更新发布文档。** `app_version.py` 与 README 开头为 1.2.3，但 README 的安装路径、完整发布目录及“当前源码版本”段仍写 1.2.2（第 88、92、100 行）。建议发布时自动检查文档中的当前版本引用。
